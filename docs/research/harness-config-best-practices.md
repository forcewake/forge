# Harness Configuration Best Practices for Unattended CI Lanes — Research (September 2026)

Purpose: configuration-level reference for forge's harness lanes (GitLab CI templates in `ci/templates/*.gitlab-ci.yml` and the GitHub Actions lane in `ci/templates/forge-harness.github.yml` + `src/forge/harness_entry.py`). This is the *policy* companion to `docs/research/harness-interfaces.md` (the per-CLI *interface* ground truth): that doc says how to invoke each CLI; this one says what the well-configured 2026 CI lane looks like — flags, briefs, instruction files, model routing, reliability, sandboxing — and ends with a ranked upgrade checklist for forge's current setup.

Tagging: **[documented]** = verified against official docs (provider docs, engineering blogs) in September 2026. **[observed]** = real-world CI configs, live binary behavior, forge's own verified findings, or community/secondary sources. Per-CLI flag syntax ground truth stays in `harness-interfaces.md`; this doc cross-references it as "HI §n".

## 1. Unattended invocation

### 1.1 Claude Code

**Recommended unattended flag set [documented]:**

- `claude -p "<prompt>"` (print mode) is the only non-interactive surface. In `-p`, "the built-in starting permission mode is Manual on every plan, so pass the permission mode you want."
- `--permission-mode acceptEdits` — auto-approves file edits plus common filesystem commands (`mkdir`, `touch`, `mv`, `cp`) inside the workspace. `dontAsk` is the locked-down alternative: "denies everything that would prompt" — best for classification/read-only lanes. `bypassPermissions` (≡ `--dangerously-skip-permissions`) approves everything except critical-path `rm`/`rmdir` and deny rules; only defensible inside an ephemeral, egress-controlled container.
- `--permission-prompts none` (v2.1.259+) — the explicit no-human guarantee for unattended runs: the run "doesn't consult any permission host"; would-be prompts are denied and surface as `permission_denied` on the final result. This is the documented replacement for relying on the historical "in `-p` mode un-allowed tools are auto-denied" behavior.
- `--allowedTools "Bash(git status:*),Read,Edit"` — allowlist auto-approvals. Note the rule-syntax subtlety the docs call out: prefix matching needs the separator — `Bash(git diff *)` with a space; `Bash(git diff*)` would also match `git diff-index`. Claude's classic `Bash(cmd:*)` colon-star prefix form is still accepted. Forge's allowlist (`Bash(git status:*)`, `Bash(git diff:*)`, `Bash(git log:*)`) uses the colon-star form and works [observed].
- `--setting-sources ''` — load no user/project/local settings, hooks, or `.mcp.json` from the checked-out repo. This matters: without it, "a `-p` session runs `.claude/settings.json` hooks and connects `.mcp.json` servers even in a folder you've never trusted" — no trust dialog exists in `-p` [documented].
- `--bare` — the newer, stronger isolation: "recommended mode for scripted and SDK calls, and will become the default for `-p`." Skips hooks, skills, subagents, plugins, MCP, auto memory, **and CLAUDE.md**; requires `ANTHROPIC_API_KEY` (never reads OAuth/keychain). Caveat for forge: `--bare` also suppresses auto-loading of `CLAUDE.md`/`AGENTS.md`-style memory, which conflicts with forge's "read the repo's conventions file" brief line — though the agent can still `Read` the file explicitly. Also [uncertain] whether `ANTHROPIC_AUTH_TOKEN` (gateway auth) satisfies `--bare`'s API-key requirement; it is documented as needing `ANTHROPIC_API_KEY` or `apiKeyHelper`.
- Output: `--output-format stream-json --verbose` for NDJSON events (terminal `result` carries `usage`, `permission_denials`, `total_cost_usd` estimate); `system/api_retry` events expose provider-level retries; `system/init` carries `plugin_errors` / `mcp_server_errors` to check in CI "since the run still exits cleanly."
- Budget/limits: `--max-turns N` (errors when reached), `--max-budget-usd <n>`.

**"Leave changes in working tree, never commit/push" [documented + observed]:** Claude Code has no native "no-commit" flag — it is enforced by composition: (a) the brief's output contract (`src/forge/harnesses/prompt.py`), (b) an allowlist whose only Bash grants are read-only git (so `git commit` is not auto-approved and would be denied under `--permission-prompts none`), and (c) the lane's git remote with push disabled. Belt-and-braces: add `--disallowedTools "Bash(git commit:*)",Bash(git push:*)"` so even a `bypassPermissions` escalation is blocked (deny rules and hooks still apply under bypass) [documented rule interaction; HI §2].

**Pitfalls [documented unless noted]:**

- Root/sudo: `--dangerously-skip-permissions` refuses to run as root (typical GitLab docker executor). The `IS_SANDBOX=1` bypass is a community workaround, not documented, and reports say it has been patched out in some versions (claude-code issues #927, #9184) [observed]. Forge's claude template sets `IS_SANDBOX: "1"` but uses `acceptEdits`, which never needs it [observed in `ci/templates/claude-code.gitlab-ci.yml`] — harmless but misleading; the honest root-safe posture is "acceptEdits + allowlist works as root; bypass does not."
- Hangs/waits: background tasks are killed ~5 s after the result; background subagents cap the wait at 10 minutes of idle (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`); slow stream consumers cap the final drain at 30 s. A missing permission mode in `-p` + a tool that asks = the run stalls or denies; always pair `-p` with a mode (or `--permission-prompts none`) [documented].
- stdin is read (cap 10 MB); SIGTERM → exit 143 with no result message; resumable via `--resume <session_id>`.
- Provider timeouts: `API_TIMEOUT_MS` (default 600 000 ms) — gateway lanes need this raised; z.ai's own setup script sets `3000000` [documented].

### 1.2 Grok Build CLI

**Recommended unattended flag set [documented]:**

- `grok -p "<prompt>"` (also `--prompt-file <PATH>` / `--prompt-json`); "Headless mode does not read piped stdin into the prompt."
- Approval: `--always-approve` (alias `--yolo`, ≡ `--permission-mode bypassPermissions`) is the documented CI posture: "For automation that must run tools without interactive approval, use always-approve (and deny rules if you need hard blocks)." Alternative modes now documented: `default` (ask), `acceptEdits`, `plan`, `auto`, `dontAsk`. In non-interactive runs, `auto` **fails** disallowed calls and reports back to the model (no hang), and `dontAsk` is the "strict CI allowlist" mode. Always-approve and auto are mutually exclusive; always-approve wins.
- Hard limits without human approval: `--allow <RULE>` / `--deny <RULE>` are "always enforced" regardless of mode (`deny > ask > allow`; a built-in dangerous list re-prompts even with remembered prefixes — but in headless that means the call fails, not hangs). `--tools` / `--disallowed-tools` filter whole tools (headless-only flags; ignored with a warning in TUI). Example straight from the docs: `grok -p "Deploy" --always-approve --deny 'Bash(rm -rf *)'`.
- `--no-auto-update` in CI (or `GROK_DISABLE_AUTOUPDATER=1`, or `[cli] auto_update = false`); update messages go to stderr, stdout stays clean for JSON formats; a non-TTY stderr is auto-detected as a suppressor.
- Output: `--output-format streaming-json` (NDJSON; `end` is always last and carries the run-aggregate `usage`/`modelUsage`) or `--output-format json` (single terminal object with `text`, `stopReason`, `total_cost_usd`).
- Limits: `--max-turns <N>`; no dollar-budget flag exists ("Budget feature doesn't exist").
- Project rules need trust: "headless startup with project rules needs `--trust` or a prior grant" [documented] — a checked-out repo's `AGENTS.md` is *not* loaded unattended unless trusted.
- `--sandbox <PROFILE>` exists (profile names documented in the sandbox page; docs' recommended layering for untrusted code: `dontAsk` + narrow allows or restrictive hook → `--sandbox strict` → project trust) [documented].

**"Leave changes in working tree" [documented]:** no rollback on interrupt — "File modifications by tools are **not rolled back**" — so the working tree is always the full candidate, including partial work after a kill. Enforcement of no-commit/push: `--deny 'Bash(git push:*)'` + `--deny 'Bash(git commit:*)'` (deny beats always-approve), plus the lane's `git remote set-url --push origin FORBIDDEN` [observed in forge's template].

**Pitfalls [observed unless noted]:**

- **Headless hangs without an approval escape**: forge verified live (grok 1.0.30) that `grok -p` without `--always-approve` hangs waiting for approval; docs don't state it, but every doc'd CI example includes `--yolo`, and bidirectional approval is delegated to ACP mode only [documented implication + forge ground truth].
- **The npm optionalDependency hang**: the wrapper declares its platform binary (`@xai-official/grok-linux-x64`) as an optionalDependency; a flaky registry silently skips it and the CLI hangs forever at startup (silent futex wait). Install both packages explicitly, pinned to the same version, with retries, and `test -d` the binary dir — forge's preamble does exactly this [observed, verified live].
- Auth in CI: "Pre-populate `auth.json` or use `XAI_API_KEY`" [documented]. Forge ships the full OAuth bundle as `FORGE_GROK_AUTH` (self-refreshing) [observed]; `XAI_API_KEY` is the cleaner pay-per-token automation path (session token wins over the env var, so a stale `auth.json` silently overrides it) [documented precedence].
- Exit codes: 0 / 1 (auth, network, runtime) / 130 (SIGINT) / 143 (SIGTERM). `cost_is_partial: true` omits all cost floats; absent cost means "unreported or incomplete, never free" — forge's "unknown, never zero" usage rule matches the vendor's own semantics [documented].

### 1.3 OpenCode

**Recommended unattended flag set [documented]:**

- `opencode run "<prompt>"` with `--auto` — "auto-approve permissions that are not explicitly denied"; explicit `"deny"` rules still enforced. This is the documented unattended contract; anything left as `"ask"` prompts on the terminal (once/always/reject) and cannot be answered headlessly.
- Permission config (`opencode.json`, or injected via `OPENCODE_CONFIG` / `OPENCODE_CONFIG_CONTENT` env): keys `edit`, `bash` (pattern-matched, last-match-wins), `webfetch`, `external_directory`, `doom_loop`, etc. Defaults: most keys `allow`, but **`external_directory` and `doom_loop` default to `ask`** — a headless hang source. A blanket `"permission": "allow"` is the ephemeral-container posture; the safer variant adds explicit denies: `{"bash": {"git push *": "deny", "git commit *": "deny"}}`.
- Observability: `--format json` ("raw JSON events") for a parseable event stream; global `--print-logs --log-level DEBUG|INFO`. Model via `-m provider/model` or config `model`; reasoning effort via `--variant`.
- Robust path for repeated invocations: `opencode serve` + `opencode run --attach http://localhost:4096` — avoids "MCP server cold boot times on every run" and gives first-class abort over HTTP.
- There is also a native GitHub Action integration: `anomalyco/opencode/github@latest` behind `opencode github install`, with `model`, `agent`, `prompt`, `mentions`, `use_github_token` inputs — issue/comment/schedule-triggered automation [documented].

**"Leave changes in working tree" [observed + documented]:** no native constraint; forge enforces via brief + push-disabled remote. The documented permission map is the mechanical layer (`git push *` / `git commit *` deny rules survive `--auto`).

**Pitfalls:**

- `ask` hangs in headless/server mode — known issue (anomalyco/opencode #14473); the GitLab template's brief must live inside the workspace because out-of-project reads trip the `external_directory: ask` default and stall [observed in `ci/templates/opencode.gitlab-ci.yml` + documented config key].
- **No parseable usage receipt on stdout in default mode** — usage lives on message info via the server API, not the CLI stream; forge records `usage: null` (unknown, never zero) [observed]. `--format json` narrows this gap but the receipt schema is version-sensitive [uncertain].
- **Exit codes undocumented** [documented gap] — classify from output/artifacts, not exit status alone.
- Forge installs via `curl -fsSL https://opencode.ai/install | bash` — unpinned and un-retried [observed]; `npm install -g opencode-ai@<version>` is the documented npm channel and matches the other two drivers' pinned+retried pattern.

### 1.4 Cross-driver comparison (configuration view)

| Dimension | Claude Code | Grok Build | OpenCode |
|---|---|---|---|
| Unattended approval | `--permission-mode acceptEdits` + allowlist (+ `--permission-prompts none`) | `--always-approve` + `--deny` rules (or `--permission-mode dontAsk`) | permission map + `run --auto` |
| No-commit enforcement | deny via `--disallowedTools` | deny via `--deny 'Bash(git push:*)'` | permission `bash` deny rules |
| Isolation from repo config | `--setting-sources ''` or `--bare` | no trust → skip rules, or `--trust` deliberately | `OPENCODE_CONFIG_CONTENT` inline config |
| Hang modes | missing permission mode; unanswered asks | no `--always-approve`; missing platform binary; `ask` rules; `external_directory` ask | `ask` in permission map; `external_directory` ask |
| Native budget | `--max-turns`, `--max-budget-usd` | `--max-turns` | none CLI-side (server abort) |
| Usage receipt | per-turn `result.usage` | per-response `usage` + run-aggregate `end` | none on CLI stdout (server API only) |

## 2. Prompt/brief quality — how the major factories brief agents

**Plan-first vs issue-first [documented]:** every major harness product converged on *plan-first with an issue as the source of truth*: Claude Code's own GitLab/GitHub lanes take the task from the issue/comment payload (`AI_FLOW_INPUT` from a webhook, `@claude` mention, or an automation `prompt:` input) and every product ships a plan mode as the entry to complex work — Anthropic: "separate exploration from execution… use it when the approach is uncertain, changes span multiple files, or the code is unfamiliar"; xAI: "For complex tasks, start Grok Build in plan mode. You can approve the plan… before execution." OpenAI's codex-action takes `prompt`/`prompt-file` inputs and Codex emits a native plan-update item in its event stream. Forge's shape — human-approved plan (digest-bound) fetched from the tracker and rendered into a brief file, with the per-CLI `-p` prompt as a short pointer — is exactly the automation-mode pattern the vendors document (`prompt:` inputs; `--prompt-file`), and it survives the issue→run handoff that interactive lanes don't need [documented + observed].

**What goes in the brief — the convergent checklist [documented]:**

1. **Acceptance criteria as a machine-checkable artifact.** Anthropic's long-running-agent harness writes an explicit feature list where each item starts `"passes": false` and agents may only toggle that field: "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality" (JSON chosen over Markdown because models alter JSON less). The general lesson: criteria the *lane* can re-verify, not prose.
2. **A verifiable check.** Anthropic best practices: "Give Claude a check it can run: tests, a build, a screenshot to compare," and "show evidence rather than asserting success."
3. **File scope and existing patterns.** "Reference specific files, constraints, and example patterns"; point at a known file that embodies the pattern to copy (this is the few-shot mechanism — pointing at code beats embedding snippets).
4. **Constraints as deny-lists**, not vibes: dependency policy, forbidden paths (CI/config files), style deltas only ("Bash commands Claude can't guess," style rules that differ from defaults — exclude "self-evident practices like 'write clean code'").
5. **Context ordering.** Anthropic's harness opens every session with a fixed sequence: run `pwd`, read the progress file, read the feature list, `git log --oneline -20`, run the environment `init.sh`, then a smoke test — before touching new work. A deterministic re-orientation ritual is the documented countermeasure to "engineers working in shifts" amnesia across context windows.
6. **The output contract at the end, in imperative voice** (commit/push rules, where to leave results).

**Anthropic-specific guidance for long/unattended Claude tasks [documented]:** plan mode first (cheap: "If you could describe the diff in one sentence, skip the plan"); `--append-system-prompt` / `--append-system-prompt-file` for invariant instructions that must outrank the user prompt (their own PR-review CI example pipes `gh pr diff | claude -p --append-system-prompt …`); subagents for verification ("a reviewer sees only the diff and the criteria you give it… tell the reviewer to flag only gaps that affect correctness"); keep `CLAUDE.md` short because "a bloated file means Claude ignores your actual instructions."

**OpenAI Codex guidance [documented]:** the brief lives in `AGENTS.md` (working agreements: test commands, package-manager preference, "confirmation requirements before adding production dependencies"); unattended runs pair `codex exec` with `--ask-for-approval never` + `--sandbox workspace-write`; `codex exec -` reads the prompt from stdin, `--output-schema` constrains the final message, and CI should "run linters, tests, and type checks" as the verification layer rather than trusting agent self-report.

**xAI Grok guidance [documented]:** plan mode first for complex tasks; `--rules "<text>"` appends per-run rules to the system prompt and `--system-prompt-override` replaces it (the grok equivalents of forge's brief/`--append-system-prompt` split); "short, specific instructions are followed more reliably than long ones" (their rules page, which also warns rules files "are loaded in full, with no size cap").

**Forge's brief (`src/forge/harnesses/prompt.py`) vs this checklist [observed]:** Role → Task (issue snapshot) → approved plan verbatim + digest → Constraints (deps, denied paths, style, minimal diff) → Quality bar (run relevant tests to green; conventions file first; read before writing) → Output contract (no commit/push; never touch `.forge/`). It matches items 3–6 well. Gaps against the 2026 state of the art: no explicit **acceptance-criteria checklist** derived from the plan (item 1), no **commands-to-verify** block (which test command exactly), and the binding output contract lives only in the brief file — the vendors' pattern is to also push invariants into the system-prompt layer (`--append-system-prompt` for Claude, `--rules` for Grok) so a confused agent can't "lose" them.

## 3. Skills / instruction files

**CLAUDE.md resolution [documented]:** load order broadest→most specific: managed policy (`/etc/claude-code/CLAUDE.md` on Linux, cannot be excluded) → `~/.claude/CLAUDE.md` → `./CLAUDE.md` or `./.claude/CLAUDE.md` → `./CLAUDE.local.md` (gitignored). All discovered files **concatenate** (root down to cwd), they don't override; nested subdirectory `CLAUDE.md` loads on demand when Claude reads files there. `@path` imports expand at launch (max depth 4; outside-cwd imports need approval); `claudeMdExcludes` skips files by glob; target "under 200 lines per CLAUDE.md," files >4 MiB are skipped. New: `.claude/rules/*.md` load at launch like CLAUDE.md, with YAML `paths:` frontmatter scoping rules to file globs — the right home for "only when touching `src/api/**`" conventions.

**`.claude/skills` and `.claude/commands` [documented]:** `.claude/skills/<name>/SKILL.md` (frontmatter `name`, `description` — drives model-invocation, `allowed-tools`, `disable-model-invocation`, `context: fork`, …); `.claude/commands/<file>.md` creates the same `/command` surface. Progressive disclosure: descriptions sit in context; bodies load on use. `!`-command lines inject live command output into the skill before the model sees it. Versions: no native version field — versioning is git (commit skills to the repo) plus plugin marketplaces; `metadata` is free-form for your own tooling.

**AGENTS.md family — per harness [documented]:**

- **Codex:** `AGENTS.override.md` > `AGENTS.md` > fallbacks (`project_doc_fallback_filenames`); one file per directory walking from git root down to cwd, concatenated root-down (closer-to-cwd wins by appearing later); global `~/.codex/AGENTS.md` (or `$CODEX_HOME`); combined size capped at 32 KiB (`project_doc_max_bytes`).
- **OpenCode:** per category, "first matching file wins": project `AGENTS.md` > `CLAUDE.md` (fallback), global `~/.config/opencode/AGENTS.md` > `~/.claude/CLAUDE.md`. Extra files via `"instructions": ["docs/guidelines.md", "packages/*/AGENTS.md"]` (globs, plus remote URLs with a 5 s timeout). Claude-compat fallbacks (skills at `~/.claude/skills/`) can be disabled with `OPENCODE_DISABLE_CLAUDE_CODE=1`.
- **Grok Build:** per directory reads `AGENTS.md`, `Agents.md`, `AGENT.md`, `CLAUDE.md`, `Claude.md`, `CLAUDE.local.md`, plus `*.md` under `.grok/rules/`, and also reads `.claude/rules/` and `.cursor/rules/` for compatibility; gitignored files are skipped; deeper files win; **no size cap** ("short, specific instructions are followed more reliably"); `grok inspect` lists every loaded rules file with token counts — use it in CI debug output. Global rules in `~/.grok/`. Headless needs `--trust` (or a prior grant) before project rules load.

**How factories provide conventions + versioning [observed]:** the common shape is (a) commit `AGENTS.md`/`CLAUDE.md` + `.claude/skills/` to the *target* repo so the lane inherits conventions from the checkout itself (what forge's brief directs), and (b) keep *factory-owned* prompts/skills versioned in the factory repo and pinned by ref when injected (forge pins its own `filter.mjs` fetches and the harness_entry install ref; the plan/brief is digest-bound in the RunSpec). Vendor docs agree versioning is "git + marketplace," i.e., pin the ref, review instruction diffs like code.

**Injection from untrusted repos — the 2026 threat model [documented + observed]:**

- Claude Code: without isolation, a `-p` run "in a folder you've never trusted" still executes `.claude/settings.json` hooks and connects `.mcp.json` servers [documented]; a project skill's `allowed-tools` "grants bypass permission prompts … even in untrusted `-p` runs — so review the `allowed-tools` of skills checked into a repository before you run Claude Code there" [documented]. Mitigations: `--setting-sources ''` / `--bare` (forge does the former), `permissions.deny` rules which "apply right away even before workspace trust," `disableSkillShellExecution` in managed settings.
- Codex exec: the Backslash July-2026 PoC — a malicious committed `AGENTS.md` executes silently *before* the user's task in exec mode; `workspace-write` "restricts writes but imposes no read restrictions," so `~/.aws/credentials`, `~/.gitconfig`, `~/.npmrc` were readable and stageable (network off by default limits exfiltration). Mitigations they recommend: containerize agents; block reads of credential paths; treat instruction files as supply-chain artifacts to scan (credential paths, network calls, obfuscation); "enforce exec-mode policy at the platform layer"; version/attribute/monitor `AGENTS.md` changes [documented research + observed].
- Grok/opencode: same class of risk (implicit-trust config files); grok's `--trust` gate and `grok inspect` audit, opencode's first-match-wins + explicit config, are partial mitigations [documented].

**Forge posture [observed]:** correct on the big levers — Claude runs with `--setting-sources ''` (no repo hooks/MCP/settings), the lane is proposal-only with no write credential and no network need beyond the model API, and the trusted publisher rejects CI/config changes, so an injected "edit the pipeline" instruction fails downstream. Residual risks worth closing: grok loads the target repo's `AGENTS.md`-family *only if* trusted (today forge passes neither `--trust` nor isolation — [verify] which happens on the current image), and nothing in the lane treats instruction-file diffs as suspicious (the publisher gate is the only backstop — acceptable, but document it as the control).

## 4. Model selection & routing

**Current lineups (September 2026) [documented]:**

- **Anthropic:** `claude-opus-5` (recommended default "for complex agentic coding and enterprise work"), `claude-sonnet-5`, `claude-fable-5-1` (1M context; "for demanding reasoning and long-horizon agentic work" when Opus 5 at higher effort falls short), `claude-haiku-4-5-20251001` (200K; Haiku 4.5 ≈ Sonnet 4's coding performance). Legacy still served: `claude-opus-4-8`, 4.7, 4.6, 4.5, `claude-sonnet-4-6`, `claude-sonnet-4-5`. Since the 4.6 generation, **dateless IDs are themselves pinned snapshots**, not floating "latest" aliases — pinning guidance is therefore "use the dateless ID of the generation you validated" rather than fear of alias drift. Bedrock/Vertex need provider-prefixed forms (`us.anthropic.claude-sonnet-4-6`).
- **xAI:** `grok-4.6` is the flagship and Grok Build's default ("for everything else, including code, use Grok 4.6"), `grok-4.5` alongside. The 2025-era `grok-code-fast-*` names no longer appear in the current model list. Reasoning effort via `--effort <LEVEL>`.
- **Z.ai / GLM (gateway):** server-side default mapping for Claude Code clients is `opus→GLM-4.7`, `sonnet→GLM-4.7`, `haiku→GLM-4.5-Air`; newer `GLM-5.3` / `GLM-5.3-Flash` (MoE ~320B/18B-active, multimodal; community pricing ≈ $1.40/$4.40 per M tokens; "Flash" benchmarked against Opus 4.8-class at ~10× lower cost) are selectable by explicit model override. Z.ai explicitly recommends **not** hardcoding the tier mappings so gateway-side upgrades flow through [documented].

**Gateway env pattern (z.ai-like) [documented]:**

```bash
export ANTHROPIC_BASE_URL=https://api.z.ai/api/anthropic
export ANTHROPIC_AUTH_TOKEN=<zai key>        # NOT ANTHROPIC_API_KEY
export API_TIMEOUT_MS=3000000                # z.ai's own setting for long requests
# optional tier mapping instead of a hard model pin:
# ANTHROPIC_DEFAULT_OPUS_MODEL / ANTHROPIC_DEFAULT_SONNET_MODEL / ANTHROPIC_DEFAULT_HAIKU_MODEL
```

Claude Code tier-routing env vars (`ANTHROPIC_DEFAULT_HAIKU_MODEL` etc.) let the *agent's internal* small-model calls (summaries, titles, classification) hit the cheap tier even when the main loop is pinned — the mechanism factories use for cheap-vs-strong without changing the CLI invocation. `ANTHROPIC_MODEL` overrides everything; `ANTHROPIC_DEFAULT_MODEL` applies only when no settings file sets `model`; `fallbackModel` is an ordered chain read from the highest-precedence file that defines it [documented].

**How factories route per phase [documented + observed]:** plan and review get the strong tier, implementation the value tier, classification/triage the small tier — realized as (a) per-phase model args in the factory's driver invocation (forge's RunSpec carries a model route per step [observed]), (b) harness-native knobs: OpenCode `small_model` + per-request `model` + `--variant` (reasoning effort), Claude `ANTHROPIC_DEFAULT_*_MODEL` + `fallbackModel`, Grok `--effort`, Codex `effort`/`-m`; and (c) same-family routing per phase to preserve prompt caching (cache_read receipts show up in all three usage streams). Pin **snapshots per phase** for reproducibility; keep the pin in the RunSpec/factory config, not in per-repo templates, so an upgrade is a factory release, not an onboarding migration [observed — this is forge's current design; the templates' `ANTHROPIC_MODEL: "glm-5.3-flash[1m]"` hardcode is the exception to it].

## 5. Reliability in CI

**Timeouts — four nested layers [documented + observed]:**

1. CI job wall clock: GitLab `timeout: 30m` (forge's value) / GitHub `timeout-minutes: 60` (forge's Actions value). Anthropic's GitLab docs also call out job-level `timeout` as the runaway guard [documented].
2. Provider/API layer: Claude `API_TIMEOUT_MS` (default 600 000 ms — too low behind gateways; z.ai sets 3 000 000), `MCP_TIMEOUT` (default 30 s startup).
3. Tool layer: Claude `BASH_DEFAULT_TIMEOUT_MS` (120 s) / `BASH_MAX_TIMEOUT_MS` (600 s) — an implementation agent that runs the test suite needs these raised or its `pytest` gets killed at 2 minutes and it flails [observed pattern]; OpenCode per-provider `timeout`/`headerTimeout`/`chunkTimeout` in the provider config.
4. Agent-loop layer: `--max-turns` (Claude, Grok) so a looping agent dies before the job timeout with a parseable cause; Claude `--max-budget-usd` for the dollar guard.

**Retries & flaky installs [observed + documented]:** forge's 3× npm retries with backoff are the right shape; the grok template's platform-binary re-install + `test -d` check is the standout (a silently-skipped optionalDependency otherwise hangs the CLI at startup). The claude GitLab template still does a single unpinned `npm install -g @anthropic-ai/claude-code` [observed] — inconsistent with both its Actions sibling (which retries) and the grok template. Claude's `system/api_retry` events make provider retries visible in the stream — surface them in the filter so "it was slow because the API 429'd five times" is diagnosable from the trace [documented].

**Caches [documented]:** GitLab `cache:` keyed on lockfiles (`cache:key:files: [package-lock.json]`, `policy: pull` for harness jobs that only read) aimed at the npm global/cache dir (`npm_config_cache`), and `actions/setup-node` with `cache: npm` on the Actions side. Caches don't remove the need for retries (registry 5xx ≠ cache miss) but they cut the flake surface and minutes. Forge has no cache in any lane [observed].

**Log streaming & token limits [observed + documented]:** forge's pattern — tee the full NDJSON to a file, pipe a compacted/filtered view into the live job trace, tail the raw debug log on silent stalls — matches what the vendors enable (`--output-format stream-json`, grok's `--debug-file`, opencode's `--print-logs`). Watch per-step log ceilings on GitHub-hosted runners when streaming raw deltas; the compacted filter view is what keeps traces within them [observed]. `BASH_MAX_OUTPUT_LENGTH` (default 30 000 chars) caps what Claude will ingest from a command [documented].

**Artifact collection [observed]:** upload `if: always()`/`when: always` with short retention (forge: 7 days), `git diff --binary --full-index` vs the frozen base, and `if-no-files-found: error` on the Actions side so an empty candidate fails loudly. Keep control files (`.forge/brief.md`, debug logs) out of the artifact — they are context, not deliverable [observed, correct].

**Flaky-exit handling [observed, forge's design is the best practice]:** `set -o pipefail` through the tee/filter so the driver's exit code survives; classify failure from the driver exit *and* the terminal event (Claude `result.is_error`, grok `end.stopReason`), never from harness claims in the trace; the lane always exits 0 and lets the artifact's meta `exit` field classify, so a red driver never destroys the audit trail. This mirrors the vendors' own warnings: opencode exit codes undocumented, grok "absent cost means unreported, never free," Claude SIGTERM=143 leaves "no result."

**Running as non-root [documented + observed]:** GitLab docker executors run as root; Claude refuses `--dangerously-skip-permissions` as root and the `IS_SANDBOX=1` escape is undocumented and fragile (issue #9184 reports it patched out) [observed]. The honest postures: (a) permission-mode + allowlist that works as root (forge's claude lane), (b) a rootless user in the image (Anthropic's devcontainer reference is rootless by design), (c) codex-action's documented `safety-strategy: unprivileged-user` as the vendor-blessed shape. Prefer (a) today; note (b) as the direction if bypass modes are ever needed.

## 6. Sandboxing & security

**Claude Code sandbox mode [documented]:** a sandboxed Bash tool enforced by the OS — macOS Seatbelt; Linux needs `bubblewrap` + `socat` (optional seccomp via `@anthropic-ai/sandbox-runtime`); in unprivileged containers `enableWeakerNestedSandbox: true`. Enabled via `/sandbox` or settings (`sandbox.enabled`, `sandbox.allowUnsandboxedCommands` for strict mode, `sandbox.network.allowedDomains` — **no domains pre-allowed by default**, leading-`*` wildcards only — `sandbox.filesystem.denyRead/denyWrite/allowRead/allowWrite`). Writes default to cwd + TMPDIR + `--add-dir`; reads default to the whole machine and should be tightened in CI. Protected paths (`.claude/`, `.mcp.json`, shell startup files, `.gitconfig`) are write-denied even in writable dirs. Credential masking: `sandbox.credentials.files/envVars` with `deny`/`mask` modes; `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` strips secrets from all subprocess envs. Limits the docs admit: the network proxy decides from the client-supplied hostname without TLS inspection (domain fronting can bypass), and it only constrains Bash subprocesses. It is **not** a permission mode — it composes with one. **No `--sandbox` CLI flag exists** despite the flag-name intuition.

**Grok [documented]:** `--sandbox <PROFILE>` (strict profile named in the docs' recommended layering for untrusted code: `dontAsk` + narrow allows → `--sandbox strict` → project trust); deny rules are mode-independent; hooks **fail open** ("if a hook script crashes, times out, or is missing, the tool call proceeds") so a hook is not a security boundary unless it self-handles errors; the built-in read-only shell list is "a convenience, not a security boundary."

**OpenCode [documented]:** no OS sandbox; the permission map is the boundary — which is why explicit `"deny"` rules that survive `--auto`, and `external_directory` control, are the documented unattended recipe.

**Network egress [documented + observed]:** what top lanes lock down: (a) default-deny egress with an allowlist of exactly the model API + package registry + VCS host (Anthropic's devcontainer reference ships a firewall; GitLab's docs: "strict network and filesystem rules"; StepSecurity's Harden-Runner writeup is the observed Actions-side implementation); (b) `persist-credentials: false` on checkout so the runner token doesn't sit in `.git/config` awaiting an injected `curl` (the actsense unsafe-checkout writeup flags workflows that skip it; note claude-code-action issue #1236 — the official action itself breaks under `persist-credentials: false` in some branch setups, so test the combination); (c) least-privilege workflow `permissions:` (`contents: read` for the agent job; write only in a separate publishing job — OpenAI's codex-action "two-job pattern" is the vendor-documented version of forge's lane/publisher split); (d) OIDC instead of long-lived keys where available (claude-code-action supports Anthropic federation; GitLab `id_tokens:`) [documented].

**Secret hygiene [documented + observed]:** masked+protected CI variables; per-lane keys that are *not* the factory's keys (forge: harness credentials injected per-repo, "never forge's publisher token" — matches the vendors' guidance); the read-token-only proposal lane with `git remote set-url --push origin FORBIDDEN` is stronger than any prompt-level "don't push" instruction [observed]; rotate harness keys on a schedule (forge `docs/operations/token-rotation.md` [observed]); auth bundles on disk at `0600` (grok `auth.json`); never commit keys to the repo (both vendors' first security note); treat consumer-subscription OAuth in CI as a ToS problem, not just a security one (Anthropic: API-key auth for automation; `--bare` enforces it mechanically) [documented].

## 7. Verdict for forge — ranked top-10 configuration upgrades

Context: forge's three GitLab templates (`ci/templates/{grok,claude-code,opencode}.gitlab-ci.yml`) and the Actions lane (`ci/templates/forge-harness.github.yml` + `src/forge/harness_entry.py`) already implement the hard 80% correctly: proposal-only lanes, push disabled by construction, frozen attempt base, artifact handoff, `pipefail` + always-upload audit trail, grok's verified hang workarounds, Claude settings isolation. The ranking below is what closes the remaining gap to the 2026 vendor-documented posture. Diffs are sketched against the current files.

1. **Pin and unify CLI provisioning in all three lanes (highest leverage, pure reliability).** `opencode` installs via unpinned `curl | bash`; `claude-code` GitLab does a single unpinned npm install while its Actions sibling retries; nothing is version-locked, so a CLI release can silently change lane behavior. Introduce `FORGE_CLAUDE_VERSION` / `FORGE_GROK_VERSION` / `FORGE_OPENCODE_VERSION` project variables (factory-supplied defaults), route opencode through `npm install -g opencode-ai@${FORGE_OPENCODE_VERSION}` with the same retry loop, and add retries+pin to the GitLab claude preamble (copy `harness_entry`'s loop). Log `--version` into the trace next to `candidate.meta.json` (add `"cli_version"`).
2. **Make "never commit/push" mechanical in every driver, not just contractual.** Claude: add `--disallowedTools "Bash(git commit:*)",Bash(git push:*)"`. Grok: add `--deny 'Bash(git commit:*)' --deny 'Bash(git push:*)'` (deny survives `--always-approve`). OpenCode: replace the blanket `"permission": "allow"` in the generated config with `{"permission": {"bash": {"git push *": "deny", "git commit *": "deny", "*": "allow"}, "external_directory": "allow"}}`. The brief stays; denial now holds even if the model disobeys or a future default changes.
3. **Add Claude's explicit no-prompt guarantee.** Add `--permission-prompts none` (v2.1.259+) to both claude invocations so "nothing can wait for a human" is a documented flag instead of inherited `-p` behavior; denied asks then land in `result.permission_denials` on the stream, which the events filter should count into `candidate.meta.json`. This retires the ambiguity the template currently papers over with a comment ("In -p mode un-allowed tools are auto-denied").
4. **Grok: `--trust` + observability.** Forge briefs tell grok to follow `AGENTS.md`/conventions, but headless grok skips project rules without `--trust` — either pass `--trust` deliberately (the lane is ephemeral and injection-gated by the publisher; document the trade-off in the template) or state in the brief that grok does not load repo rules and let the brief carry conventions verbatim. Also add `--max-turns 200` (grok has no budget flag; this is the only loop guard) and run `grok inspect` output into the debug log so rules-loading is auditable in the trace.
5. **Give opencode an event stream and a usage receipt path.** Switch to `opencode run --auto --format json ... | tee .forge/events.jsonl` under `pipefail` (mirroring the other two drivers; `--format json` emits raw JSON events), and record in meta whether a receipt was parseable. Also raise the generated provider config with `"timeout": 600000` so gateway slowness doesn't surface as a mysterious driver failure. Long-term option: `opencode serve` + `--attach` inside the job to kill MCP cold-start and get first-class abort.
6. **Timeout/turn budgets as an explicit matrix.** Today only the claude lane sets `API_TIMEOUT_MS`. Standardize per driver: job `timeout: 30m`; claude `API_TIMEOUT_MS=3000000` (gateway reality), `BASH_DEFAULT_TIMEOUT_MS=300000`, `BASH_MAX_TIMEOUT_MS=600000`, `--max-turns`; grok `--max-turns`; opencode provider timeout. Rule of thumb: loop guard < tool timeout < job timeout, so every failure dies with a parseable cause instead of the job clock.
7. **npm cache in both CI systems.** Add GitLab `cache:` (`key: files: [package-lock.json]`, `paths: [.npm/]`, `policy: pull`) with `npm_config_cache` env, and `actions/setup-node@v4` with `cache: npm` before the driver step on Actions. Keeps the grok platform-binary flake (item: registry flakiness) rare instead of merely survived, and cuts minutes on every run.
8. **Move model pins into the RunSpec; keep tier mapping on the gateway.** The claude template hardcodes `ANTHROPIC_MODEL: "glm-5.3-flash[1m]"`. Keep the pin for reproducibility but source it from `FORGE_HARNESS_MODEL` like the other lanes (the template currently ignores the variable claude's siblings use), and prefer `ANTHROPIC_DEFAULT_OPUS/SONNET/HAIKU_MODEL` mapping over a total `ANTHROPIC_MODEL` override where the gateway supports it — z.ai documents that hardcoding mappings blocks gateway-side model upgrades, and the haiku tier is where Claude internally burns cheap tokens. Add `fallbackModel` (settings `--settings '{"fallbackModel": ...}'`) for provider flaps. Document current snapshot IDs (claude-opus-5 / claude-sonnet-5 / grok-4.6 / GLM-5.3-Flash) in `docs/research/harness-interfaces.md` §model so RunSpec authors pin validated IDs.
9. **Close the secrets/egress residuals.** (a) Drop `IS_SANDBOX: "1"` from the claude template or comment it as bypass-only — it does nothing under `acceptEdits` and implies a false guarantee; (b) declare `NO_PROXY` unconditionally (not only when `FORGE_HARNESS_HTTPS_PROXY` is set) so a future proxy var can't route git/npm through the model proxy; (c) egress allowlist per lane: model API host, `registry.npmjs.org`, the VCS host — nothing else (grok needs `console.x.ai`/update hosts blocked, which `--no-auto-update` mostly covers); (d) ensure every harness credential var is masked+protected and covered by `docs/operations/token-rotation.md` (grok's OAuth bundle especially — it is a long-lived refresh token).
10. **Brief v2: acceptance criteria + verification commands + system-prompt invariants.** Extend `render_brief`: (a) an explicit "## Acceptance criteria" section (derived from the plan at planning time, machine-checkable where possible — Anthropic's `passes: false` checklist pattern); (b) a "## Verify" block naming the exact test/lint commands for the repo (from conventions file or RunSpec), replacing the generic "run the relevant subset"; (c) push the binding output contract into the system-prompt layer in addition to the brief: claude `--append-system-prompt` with the no-commit/no-push/.forge rules, grok `--rules "<same text>"` — so the contract survives even if the agent never opens the brief; (d) a fixed context-order preamble (Anthropic's re-orientation ritual: `pwd`, `git log --oneline -5`, read conventions file, read plan) to stabilize multi-window behavior. The brief file remains the single prompt source; these additions travel inside it except the two system-prompt copies.

Explicitly *not* recommended now: switching Claude to `--bare` (conflicts with conventions-file loading and [uncertain] whether `ANTHROPIC_AUTH_TOKEN` gateway auth satisfies it); grok `--permission-mode auto`/`dontAsk` as the default (documented as viable for CI, but it changes failure semantics mid-SDK-generation — revisit after `HarnessDriver` lands); OS-level Claude sandboxing in these images (bubblewrap/socat dependency + unprivileged-container friction outweighs the gain while lanes are already ephemeral, root-owned, egress-limited, and credential-free).
